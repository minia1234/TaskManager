# 작업 관리자(taskmgr.exe) 분석 — REA 기반

대상: `C:\Windows\System32\Taskmgr.exe`
- 버전 10.0.26100.8972, 서명 Microsoft (유효), SHA256 `580DDA0B…5CBD`
- PE32+ x86_64, 프로시저 17,946개, 문자열 10,854개 (REA + Ghidra 12.1.4 정적 분석)

표기 규칙: **[확인]** = REA 결과로 직접 확인, **[추정]** = 코드/문자열 정황으로 해석, **[미확인]** = REA로 확인하지 못함.

### 동작 순서 (정리)

```
타이머 틱(갱신 주기)
 ├─ NtQuerySystemInformation(5)            → 전체 프로세스 목록 (이름, CPU 누적시간, 메모리, 스레드 …)
 ├─ 프로세스마다
 │   ├─ 캐시(FNV-1a 해시, PID) 조회
 │   ├─ OpenProcess + GetProcessTimes      → 생성 시각 검증 (PID 재사용 방지)
 │   └─ 효율 모드 상태 조회 (0x4D)
 ├─ 이전 샘플과 차이(델타) 계산             → 프로세스별 CPU%     [추정: 표준 방식]
 └─ 화면 갱신 (정렬, 묶기, 히트맵 색칠)
```

## 2. CPU% 계산 방식 — 검증 상태

- **[추정]** 프로세스 CPU% = (이번 샘플과 이전 샘플의 프로세스 CPU 시간 차이) ÷ (전체 CPU 용량 차이). 이렇게 하면 모든 프로세스 합이 전체 사용률과 맞는다.
- **[미확인]** 위 공식이 Taskmgr 코드에 그대로 있는지는 REA로 확인하지 못했다. `NtQuerySystemInformation(5)`를 부르는 `FUN_14002cc90`는 **호출자가 간접 호출(함수 테이블)**이라 `procedure_callers`에 나타나지 않았다.
- **검증 방법**: 이 저장소의 `TaskMonitor`가 같은 방식으로 계산한다. 결과는 `Get-Counter '\Processor Information(_Total)\% Processor Time'`와 샘플 4회 모두 일치했다 (100.0/99.7/99.4/99.2 대 100.0/99.7/99.4/99.2). 개별 프로세스는 busy-loop 1개(이론 3.125%)에서 2.8~3.0%로 나왔다.

## 3. 왜 "CPU는 높은데 원인이 안 보이는가"

작업 관리자 기본 목록에서 원인이 안 잡히는 경우는 세 가지다.

1. **같은 이름의 프로세스가 많다.** 예: `ShaderCompileWorker.exe` 29개가 각각 약 2~3%씩 쓰면 목록 상단에서는 작아 보이지만 합치면 60~70%다. Taskmgr는 이를 `이름(개수)` 묶음 행으로 접어서 보여준다 (캡처에서 `Claude(39)` 형식으로 확인).
2. **드라이버·인터럽트 시간은 프로세스에 귀속되지 않는다.** 프로세스 시간에는 DPC/ISR 시간이 빠지므로 `System interrupts` 같은 가상 항목으로 따로 보여준다.
3. **짧게 뜨고 사라지는 프로세스.** 폴링 주기 사이에 끝난 프로세스는 기록에 남지 않는다. 이 부분은 폴링으로는 완전히 해결할 수 없고 ETW(프로세스 시작/종료 이벤트)가 필요하다 [추정, 다음 단계].

## 4. GUI 디자인 — 추출 방법과 결과

### 4-1. REA로 확인한 것

- **매니페스트** [확인]: `dpiAware=true`, `autoElevate=true`, `requestedExecutionLevel=asInvoker`, Common Controls v6, 내부 어셈블리명 `Microsoft.Windows.Diagnosis.AdvancedTaskManager`.
  → 우리 앱에는 `asInvoker`와 Common Controls v6, DPI 설정(PerMonitorV2)을 반영했다. `autoElevate`는 반영하지 않았다 (필요할 때만 관리자 권한을 올리는 방식이라 우리 앱에는 필요 없음).
- **리소스 구조** [확인]: `Taskmgr.exe` 본체에는 `MUI`, `RT_VERSION`, `RT_MANIFEST`만 있다. 화면 레이아웃 데이터는 본체에 없다.
- **한국어 MUI** `ko-KR\Taskmgr.exe.mui` [확인]: 메뉴 18개(RT_MENU), 대화상자 17개(RT_DIALOG), 문자열 테이블 다수, 단축키 1개.
- **컨텍스트 메뉴 구조** [확인, 일반 MENU 형식 디코드]: 열 머리글 메뉴 `열 숨기기 / 열 선택`, 프로세스 메뉴 `프로세스 끝내기`, 서비스 메뉴, 시작 프로그램 메뉴 `사용 / 사용 안 함 / 파일 위치 열기 / 속성`, 사용자 메뉴 등.
  → 우리 앱은 이 중 **이름별 묶기·펼치기**만 구현했다. 메뉴 기능(작업 끝내기, 열 선택)은 아직 없다.

### 4-2. REA로 확인하지 못한 것

- **[미확인] 레이아웃·색**: Windows 11 작업 관리자는 XAML 기반이라 레이아웃 데이터가 `.rsrc`에 없다. REA 정적 분석으로는 배치를 얻을 수 없었다.
- **대신 한 것**: 실제 작업 관리자 창을 캡처하고(기존 인스턴스는 건드리지 않음), 픽셀을 샘플링했다.
  - 히트맵 4단계: `#D6F1FF`, `#9CDDFF`, `#79CFFF`, `#58BEFF`
  - 배경 `#FFFFFF`, 상단 바 `#EDF3F8`, 하단 바(우리 앱) `#F3F3F3`
  - 행 높이 약 28px, 머리글 높이 약 64px(우리 앱 기준)
- **[미확인] 히트맵 단계 규칙**: 한 장의 캡처로는 규칙을 정확히 알 수 없다. 관찰값(CPU 0.9%→1단계, 1.0%·3.2%→같은 단계)에 맞춘 근사치를 썼다. 메모리는 캡처에서 크기와 단계가 단조롭게 대응하지 않았다(63.5MB가 143MB보다 진한 색). 그래서 메모리 단계는 절대 크기 기준으로 **근사**했다.
- **[미확인] 아이콘 취득 경로**: REA로 작업 관리자가 아이콘을 어디서 얻는지는 확인하지 않았다. 우리 앱은 실행 파일의 연결 아이콘(`Icon.ExtractAssociatedIcon`, 16px)을 쓴다. Microsoft 아이콘 리소스는 복사하지 않았다.

## 5. 이 저장소에 반영한 것

- 상단 바(제목 + 가운데 검색창), 페이지 머리글 `프로세스`, 오른쪽 도구(갱신 주기, 이름별 합산).
- 열 머리글에 전체 CPU/메모리 사용률을 큰 숫자로 표시. 임계치 이상이면 빨간색.
- CPU·메모리 열 히트맵, 묶음 행(`이름(개수)` + 펼침 화살표), 시스템 가상 행(DPC/인터럽트, 미귀속 커널).
- 하단 바: 기록 임계치, 임계치 이상이면 `spike-log.csv` 기록, 마지막 갱신 시각.

### 자체 검증 (`TaskMonitor.exe --selftest`)

65개 검사 중 65개 통과. 4차 추가: ETW 네트워크 교정(관리자 없이 TCP·UDP 바이트가 기대값과 일치), 프레임 측정(정보용). 3차 이후 추가: 프로세스 CPU 급증 경고(20초, 한 번만), 게임 세션 시작·끝(추정 입력으로 확인), 기록 비교 표, 리포트의 게임 세션 절, 앱 기록 경로 키. 2차 추가: PID 재사용 가드(다른 생성 시각은 거부), 효율 모드 해제 시 우선 순위 복원, 생성 시각 일치, GPU 위치(LUID→PCI)와 NVML 일치, NVAPI 버스 번호와 NVML 일치, 파일 회전, 시작·종료 추적(PID 재사용은 종료+시작), 경고 규칙(한 번만 울림, 20초 지속, 떨림 방지), 자원·활동 기록 저장과 읽기, 연결 표, 프로세스 트리, 리포트 생성, CSV 내보내기, 분석 창 내용. 디스크 검사는 NVMe·ATA 해석을 합성 데이터로 확인하고, 이 PC의 NVMe 두 개를 관리자 권한 없이 실제로 읽는다. 아이콘 검사는 로컬 `cmd.exe`(대조군)와 `\\localhost` 공유에 둔 사본을 비교한다. 테스트 대상은 우리가 띄운 `cmd → ping` 쌍뿐이다. 검사 항목은 자기 프로세스 경로·사용자·명령줄·아키텍처, CPU 샘플, 부모/자식 관계, 우선 순위, 선호도, 효율 모드 켜기/끄기, 덤프 파일, 창 없는 전환, 작업 트리 끝내기, 표 상호작용(묶음 펼치기·접기, 정렬, 선택), 서비스·시작 프로그램·세션 열거, 성능 값(메모리, 디스크·NIC·GPU 개수)이다.

### 이번에 찾아 고친 문제

- **효율 모드 조회가 항상 "꺼짐"으로 나오던 버그**: `GetProcessInformation`은 입력 구조체의 `Version`을 1로 채워야 한다. 빠져 있어서 `ERROR_INVALID_PARAMETER(87)`로 실패하고 있었다.
- **효율 모드 순서**: 우선 순위를 바꾸면 스로틀링 상태가 초기화되므로, 우선 순위를 먼저 바꾸고 스로틀링을 나중에 켠다.
- **UI 스레드 정지**: 성능 샘플(PDH 카운터)이 1회 약 1초 걸려서 화면이 1초마다 멈추고 있었다. 백그라운드 스레드로 옮겼고, GPU 카운터는 10초 간격으로 읽는다.
- **프리징 후보 (코드 검토로 찾음)**: 아래 작업은 UI 스레드에서 기다렸다. 서비스 다시 시작(최대 15초 대기), 덤프 파일 쓰기(큰 프로세스는 수십 초), 작업 트리 끝내기, 사용자 세션 작업, 파일 위치·속성·온라인 검색 열기. 모두 백그라운드 작업(`RunBackground`)으로 옮겼고, 완료 후 메시지와 목록 갱신만 UI 스레드에서 한다.
- **멈춤 기록**: UI 스레드나 작업 스레드가 2초 넘게 멈추면 `%LOCALAPPDATA%\TaskMonitor\freeze.log`에 멈춘 시간, 진행 중이던 작업 이름, 멈춘 단계 이름을 남긴다. UI 단계가 150ms, 작업 스레드 단계가 300ms를 넘어도 기록한다. 감지 기능은 임시 지연(UI 단계 3.5초, 작업 스레드 단계 3.5초)을 넣어서 확인했고, 두 경우 모두 단계 이름과 함께 기록됐다.

### 남은 한계

- 짧게 뜨고 끝나는 프로세스는 폴링으로 완전히 잡을 수 없다 → ETW 프로세스 이벤트가 다음 단계.
- 프레임 속도는 DXGI 프레젠트를 보내는 프로그램만 잰다. 프레젠트 없이 그리는 그래픽 경로는 잡히지 않는다. 게임 세션 요약의 FPS는 세션 중 샘플 평균이다.
- CPU 온도는 HWiNFO 공유 메모리를 먼저 보고, 없으면 MSI Afterburner 공유 메모리("MAHMSharedMemory", 원천 ID 0x80)를 읽는다. 2026-11-05 이 PC(Ryzen 9 7950X)에서 Afterburner로 실측했다(쉴 때 44°C, 부하 54°C). HWiNFO 쪽은 아래 설명대로 합성 메모리로만 확인했다. 이 PC에는 ACPI 열 영역 카운터가 없고(인스턴스 없음) 팬 장치도 WMI에 없어서, 다른 방법은 전용 드라이버뿐이다. HWiNFO 공유 메모리 구조는 공개 문서를 따랐고, 합성 메모리로 읽기만 확인했다. HWiNFO를 켠 실측은 아직 하지 못했다. 팬 회전수는 읽기만 하고 화면에는 아직 없다.
- "자주 시작된 프로그램"은 아직 실행 파일 이름으로 묶는다. 옛 앱 기록(이름 키)은 경로 없는 행으로 따로 남는다.
- 프로세스 트리 보기에서는 이름별 합산이 적용되지 않는다.
- 효율 모드의 이전 우선 순위 기억은 메모리에만 있다. 프로그램을 다시 시작하면 효율 모드를 켠 프로세스의 우선 순위는 보통으로 돌아간다.
- 이벤트·분석 창·리포트 화면은 자체 검증에서 내용만 확인했다. 화면 배치는 이벤트 페이지만 스크린샷으로 확인했고, 트리 보기와 분석 창은 확인하지 않았다.
- 성능 페이지의 선 색은 기본 강조색 계열로 두었고, 작업 관리자 성능 페이지를 픽셀 샘플링하지는 않았다.
- 메모리 히트맵 단계는 절대 크기 기준 근사치다(표 항목 설명 참고).
- 간헐적 멈춤의 실제 원인은 재현하지 못했다. 부하 상태(CPU 약 74%, 프로세스 430여 개)에서 120초와 150초 시험을 돌렸고, 멈춤 기록은 0건이었다. 이 시험은 페이지 전환과 우클릭 메뉴 열고 닫기만 했다. 작업 끝내기와 덤프 파일 만들기는 UI 경로로 시험했다(우리가 띄운 ping 프로세스 대상. 끝내기는 프로세스 둘을 끝냈고, 덤프는 14MB 파일 하나를 만들었다. 앱은 두 경우 모두 계속 반응했고 멈춤 기록은 0건). 아직 시험하지 않은 것: 서비스 시작·중지·다시 시작, 세션 연결 끊기·로그오프·메시지(사용자가 시험하지 않기로 함). 네트워크 경로 아이콘은 `\\localhost` 공유에서 자체 검증으로 시험했다(204ms에 추출). 응답하지 않는 실제 네트워크 공유에서의 동작은 시험하지 않았다. 서비스와 세션 작업은 이 PC의 상태를 바꾸므로 허락을 받은 뒤에 시험한다. 다시 멈추면 `freeze.log`의 단계 이름으로 원인을 확인해야 한다.
- GPU 사용률은 엔진 중 최대값이다. 작업 관리자가 어떤 값을 쓰는지는 확인하지 않았다.
